# NL2SQL 技术架构

> 企业智能问数系统：自然语言 → 查业务数据 / 查文档 / 归因分析。

---

## 0. 一句话总览

用户自然语言提问 → **Agent 自主 ReAct 循环**（查元数据 → 生成只读 SQL → 业务库执行 → 结果回灌）→ 流式回答 + 必归因。
Web 与飞书两个入口，共用同一个编排内核。

技术栈：FastAPI + SQLAlchemy 2.0(async) + asyncpg/aiomysql（平台库 PG 生产 / MySQL 测试）+ Redis（降级进程内 dict）+ openai/anthropic SDK（直连，去 langchain）+ sqlglot + RAGFlow（外部知识库）。

---

## 一、设计哲学（先读这节，后面全是它的展开）

### 1.1 一切皆技能（Everything is a Skill）

系统里**没有一行业务 if-else**。内核（Orchestrator/AgentLoop）是纯协议机器，只懂"循环、护栏、流式、收尾"；
所有业务智慧——怎么查数、怎么查文档、怎么做归因、什么时候推荐联系人——全部是**数据**（`nl_cfg_skills` 表里的 4 行）。

推论是这套系统最强的性质：**加一种能力 = 往数据库插一行，不发版**。
归因从"可选触发"改成"必须归因"，改的是一行提示词；问数从"别问口径"改成"问清勿猜"，也是一行。
运行代码的演进速度因此和业务知识的演进速度解耦了——后者快得多。

四件套的分工（能力的完整解剖）：

```
KERNEL 内核   代码   纯协议：意图三分法 + 运行铁律（中文思考/不编数/问清勿猜/及时 finish）   零业务
TOOL  工具    代码   原子能力：JSON schema 教参数 + handler 真跑                            一个工具一件事
SKILL 技能   数据   方法论：教 loop 何时/怎么组合工具；tools 字段声明依赖                     prompts 表一行
RULE  规则   数据   表的事实：粒度/口径/字段含义——挂在那张表上，查到才注入                   rules 表一行
```

新能力 = 先造 tool（决定"能不能"），再写 skill 教用（决定"何时用"），涉表知识进 rule（决定"关于这张表的真相"）。
纯 skill 长不出执行能力，纯 tool 没有方法论就是摆设——**能力 = tool × skill**，一个能力只挂一个工具，复用而非重写。

### 1.2 提示词即数据，知识按需注入（Context Economy）

三层提示词全部以数据库为单一真相源，后台热改：

| 层 | 载体 | 常驻? | 内容 |
|---|---|---|---|
| 内核 | `prompt_store.py` KERNEL_PROMPT | 常驻 | 意图识别三分法（查数/查文档/混合）、运行铁律 |
| 技能 | `nl_cfg_skills` ×4 | 常驻 | 问数方法论 / kb_qa 知识库问答 / 归因方法论 / 联系人推荐 |
| 表级规则 | `nl_md_rules` | **按需** | 粒度对齐、Btype 含义、层级过滤用法——`query_metadata` 查到那张表才注入 |

关键在第三层：**跟表走的知识挂表，不进常驻上下文**。两张表的粒度差异、七种记录类型的含义、
"禁止拿项目名当 dept_name"——这些知识只在模型看到那张表的那一秒出现，不占一个常驻 token。
原则一句话：**方法论归 skill，事实归 rule**。

### 1.3 单循环涌现，不做编排器（Emergence over Orchestration）

不建独立意图分类器（引入往返+误差，和循环内决策重复）；不建强制 planner（简单查询纯加延迟）；
不建胖工具（自包方法论+重复调库）。意图靠**工具描述区分度**（execute_sql=业务数据 / knowledge_search=文档）
+ 常驻技能方法论，在同一个 ReAct 循环里自然分流。归因不是第二个 pipeline，是问数技能里的一段方法论
+"必须归因"铁律——模型自己决定在哪一轮补查素材表。

### 1.4 可靠性是一等公民，不是补丁

每个真实故障都要沉淀成**机制**而不是修一次了事（全部来自实战，见 §十一）：
思考马拉松 → 动态墙钟；孤立代理字符 → 双端消毒；掐空闲连接 → 池心跳+收尾超时兜底；
消息补投 → 双层去重；参数截断 → 宽松解析。原则：**只处理真见过的失败**，不提前替没出现的问题写防御代码。

## 二、总体架构（分层）

```
┌─ 接入层 ──────────────────────────────────────────────┐
│  飞书机器人（WS 长连接·流式卡片·群聊@）  Web 前端（SSE·管理后台） │
├─ 编排与模型层 ────────────────────────────────────────┤
│  Orchestrator（忙闸门·prompt 装配） → AgentLoop（ReAct·护栏·动态超时） → LLMService │
├─ 提示词体系（DB 单一真相源）─────────────────────────────┤
│  KERNEL（代码） │ Skills×4（tools=声明并集） │ 表级规则（挂表热注入） │
├─ 工具层 ──────────────────────────────────────────────┤
│  query_metadata │ execute_sql │ knowledge_search │ get_sql_template │ ask_user/finish │
├─ 存储层 ──────────────────────────────────────────────┤
│  平台库(ORM) │ 业务数仓(动态连接池) │ Redis │ RAGFlow │
└─ 横切：审计(全链路 trace/event) · 安全护栏(只读校验/敏感列/次数熔断) ──┘
```

数据流：双入口 → 忙闸门 → 装配 prompt → ReAct 循环（思考→调工具→结果回灌，每轮流式外发）→ 终态收尾。

## 三、一次问数的全链路

```
飞书消息（message_id 去重防 WS 补投重跑 → 群聊回群/私聊回人，会话按 open_id 隔离）
或 Web POST /api/ask/sse
  → Orchestrator.handle_message()  async generator[SSEEvent]
      0. 会话忙闸门：同 session 已有 run 在跑 → 立即拒（拒绝也落审计）
      1. 判 resume：status==awaiting_clarification → 断点恢复
      2. 装配 system_prompt = KERNEL + 4 个 always_on skill + 当前日期
  → AgentLoop.run()  for turn in range(max_turns):
      LLM 流式生成（单轮动态墙钟：只思考不产出 150s 掐断+催促；有产出每增量续期 60s，上限 420s）
        ├ content 片段 → answer_delta（打字机）
        ├ reasoning 片段 → reasoning_delta（思考累积，终态折进面板）
        └ 工具参数增量解码 → finish 的 answer 实时外发 / execute_sql 的 SQL 实时上卡
      四道工具闸（执行前）：同参重复→回灌复用 / metadata 每轮 1 次 / SQL 上限 10 次 / 同表同 WHERE 冗余拦截
      registry.execute() → ToolResult 摘要回灌 msgs
        - execute_sql：sqlglot 校验→列校验→业务库（30s/1 万行）→ ≤200 行全量回灌（单格 300 字/总量 24K 护栏）
        - ask_user → 挂起存 checkpoint → 用户回复 → 断点恢复
      逼近上下文阈值 → _maybe_compress（按 group 摘要，保留 query_metadata 结果）
  → 末事件必为 done / clarification_needed / cancelled / error 之一
  → 收尾三步（回写历史/审计/状态转移）各 10s 超时兜底——辅助链路超时即弃，答案优先
```

**必归因路线**：只要本轮查了数，收尾前必须归因——查归因素材表（层级过滤，规则挂表），
输出带同比环比对比，每条原因标来源 `Btype·【标题】`，事实与（推测）严格分开。

## 四、编排内核（`core/`）

### 4.1 Orchestrator（`orchestrator.py`）
忙闸门（内存 `_running` 集合，防同 session 重叠冲掉审计）→ 判 resume → 装配 prompt+注入日期 → 透传 loop 事件。不含业务逻辑；状态转移由 loop 内 `SessionState` 驱动。

### 4.2 AgentLoop（`agent_loop.py`）— ReAct 循环
- **护栏**（`_limits`，admin 改 `nl_cfg_limits` 后 `reload_limits` 热更新）：

| 护栏 | 当前值 | 作用 |
|------|------|------|
| `max_turns` | 30 | 最大推理轮数 |
| `max_ask_user` | 4 | 追问上限（配合"问清勿猜"铁律） |
| `max_sql` | 10 | execute_sql 硬上限（防烧网关额度） |
| `max_sql_fail_streak` | 3 | 连续空/错 → 提示 LLM 收手 |
| `max_meta_per_run` | 1 | 每轮 query_metadata 上限 |

- **冗余 SQL 检测**（`_sql_redundant`）：sqlglot 抽 (表, WHERE, 列)，同表同谓词且列已覆盖 → 判冗余回灌复用。
- **上下文压缩**（`_maybe_compress`）：逼近 token 阈值按 group 摘要，保留最近 2 group + 全部 query_metadata 结果。
- **可靠性机制**：
  - 动态墙钟（防思考马拉松烧配额，慢答案不误伤）；
  - 孤立代理字符入口清洗（`_clean`，delta 级——流式分块切碎多字节字符会产生 `\ud835` 非法代理，不清会在编码时当场炸）；
  - 工具参数宽松解析（`_loose_parse_args`——参数 JSON 流尾截断时从残缺文本抠 sql 等字段）;
  - finish 参数打字机（`_finish_answer_piece` 增量解码 answer/sql）;
  - 空转轮守卫（思考烧穿输出上限的截断流不被当成"答完了"，催促两次才放弃）。
- `reload_registry()`：admin 改 skill 后热替换工具集。

### 4.3 SessionState（`session.py`）
状态机 `IDLE/RUNNING/AWAITING_CLARIFICATION/DONE/ERROR`。ask_user 挂起存 `LoopCheckpoint`，回答后 resume 注入为 tool 结果、删 checkpoint。`sweep_stale_suspended` 清 30 分钟以上僵死挂起。

### 4.4 AuditSink（`audit.py`）
逐事件缓冲，按 **trace_id 隔离**（并发 run 不互冲——历史上"审计没记上"bug 的修复）。finalize 写汇总行+批量事件；DB 错误吞掉不中断（收尾另有 10s 超时兜底）。

### 4.5 PromptStore（`prompt_store.py`）
`nl_cfg_skills` 是提示词单一事实源。`assemble_system_prompt()` = KERNEL + enabled&always_on skill（内存缓存，admin 改后失效）。注意缓存单进程，多 worker 不跨进程生效。

## 五、工具层（`tools/`，全原子，无胖工具）

| 工具 | 作用 | 备注 |
|------|------|------|
| `query_metadata` | 白名单表+列+关联+**表级规则(rules)** | 列分类 metric/dimension+短维度抽样真实值；300s TTL 列缓存+表级并发；手写注释(manual)优先、hidden 列不返回 |
| `execute_sql` | 只读查业务数据 | sqlglot 禁 DDL/DML+执行前列名校验（拦截幻觉字段）；30s/1 万行；≤200 行全量回灌 |
| `knowledge_search` | 检索文档片段 | RAGFlow；空/失败返回提示让 LLM 别重试 |
| `get_sql_template` | 按名取样板 SQL | 免占常驻 prompt，LLM 按需调 |
| `finish` / `ask_user` | 结束 / 澄清 | 控制流，置标志位，loop 观察 |

- **Registry**：每次 `openai_tools()` 重建 schema（防幻觉调隐藏工具）+ 参数强转 + 可用性过滤 + 超时/连接错退避重试，非可恢复错误回 ToolResult 让 LLM 自愈。
- **Catalog**：注册总入口 = 内核控制流工具 ∪ 所有 enabled skill 声明的 tools（**并集**，非按技能隔离的权限——删声明前确认没有别的技能独家依赖）。

## 六、LLM 层（`llm/service.py`）

- `chat_stream(messages, tools, purpose)`：按用途（analysis 问数 / attribution 归因）从 `nl_cfg_llm` 取配置，openai/anthropic 双协议分发。
- **限流**：RPM 时间窗 + 并发信号量（配置 None 则不限）。
- **重试**：建流阶段可恢复错误指数退避+jitter+retry-after；流中断不重试（避免重复输出），交 loop 自愈；网关转述的瞬时 400 纳入可重试。
- **思考链透传**：`reasoning_content` / `thinking_delta` → `_Chunk.reasoning`。
- **出口代理字符消毒**（`_sanitize_messages`）：发请求前递归清洗全部消息——拦"中毒会话历史回灌"（脏消息已落库，入口清洗管不了库存，出口全拦）。
- anthropic `max_tokens=16384`（推理模型思考计入预算，4096 会烧穿截断）。

## 七、飞书通道（`feishu/`）

### 7.1 Adapter
- 独立 daemon 线程跑 Lark WebSocket（SDK 有模块级全局 loop 的坑，须线程内新建并覆盖）；同步回调只做投递 `run_coroutine_threadsafe` 回主 loop——**ACK 秒回，长 run 不阻塞事件接收**。
- 并发防护两层：**message_id 去重**（600s TTL，根治 WS ACK 超时补投导致的重跑）+ **Orchestrator 忙闸门**。
- 群聊：@机器人回复到群里（chat_id），会话仍按 open_id 绑定（每人独立上下文）。

### 7.2 流式卡片（v3 形态）
平台实测约束：顶级 markdown 的 `acontent` 可靠；**折叠面板内部嵌套元素流式刷新不可靠**——因此生成期用"单清单流式"：

- 卡 body = `[思考过程清单, 答案]` 两个顶级 markdown；
- 清单每工具一行：`N. **动作** · 结果 · 距上一步Ns`（进行中/失败文字化；无 emoji、无 SQL——完整 SQL 只在终态面板）；notice 事件（"正在生成整体总结"等）也插一行；
- 答案全量打字机（finish 参数有增量解码实时外发）；
- **四种终态（完成/出错/取消/澄清）统一整卡重建折叠**：思考全文（2000 字截断）+ 全部步骤折进默认收起面板，答案在外，参考来源平铺；整卡 28KB 护栏（超限先丢思考再截步骤，保重建必过）；失败隔 1s 重试一次；
- 所有卡片 API 过 `_api_lock` 串行 + 严格递增 sequence（防 300317 乱序）。

## 九、配置分层（别放错地方）

- **yml + profile**：只放基础设施——app / redis / database（段名 database，兼容旧 postgres 段）/ feishu / auth。

## 十、业务语义层：双表粒度模型

粒度层级链：**中心 > 省分公司 > 区域 > 场站 > 项目**（从左到右包含）。
问数表（`ods.ods_monthly_ranking_ai`，Ztype 四档）与归因素材表（`app.app_oper_question_attri_wide_ai`，粒度=场站）之间三个信息差，全部以表级规则封死：

| 信息差 | 事实 | 规则对策 |
|---|---|---|
| 粒度差 | 问数表无场站档 | 场站级信息一律去素材表 |
| 名称差 | 问数表下钻的 project 是项目名≠场站名 | 禁止拿项目名 dept_name IN 查素材表；跨表在省分公司/区域两级同名对齐 |
| 集合差 | 问数表只收经营口径需关注的场站（子集），素材表全量（超集） | 数目对不上是正常的，不互相对账 |

模型跨表心智模型：**上级对齐 → 场站级以素材表为准、用上级字段过滤进去找（GROUP BY dept_name 定位）**。

## 十一、可靠性工程（故障 → 机制，全部实战）

| 故障（现象） | 机制（对策） |
|---|---|
| 推理模型思考马拉松：11 分钟烧穿配额 | 动态墙钟：只思考不产出 150s 掐断+催促；有产出续期，正常长答案不误伤 |
| 孤立代理字符（`\ud835`）炸请求/卡片/MySQL | 入口清洗（delta 级）+ 出口消毒（整消息递归）双端拦截，中毒历史回灌也拦 |
| 华为云掐空闲连接不发 RST → run 结尾落库永等 | 连接池 pre_ping+recycle、Redis socket_timeout+keepalive、收尾三步 10s 超时兜底 |
| 飞书 WS ACK 超时补投 → 同一问题跑 N 个 run | message_id 去重表 + 会话忙闸门双层 |
| 工具参数流尾截断 → "未提供 SQL"连发 | 宽松解析从残缺 JSON 抠字段 |
| 卡片并发写 seq 乱序（300317） | 全部卡片 API 过串行锁，seq 分配原子 |
| 长文本整卡超限被拒 → 终态不折叠 | 28KB 护栏降级链 + 重建失败隔 1s 重试 |

## 十二、设计原则与不做的事

**原则**：极简内核零业务；能力 = tool × skill、知识 = rule；热更新优先于重启；优雅失败优于重型防御；意图涌现不分类器；只处理真见过的失败。

**不做（防过度工程边界）**：
- 独立意图分类器（往返+误差，与循环内决策重复）
- 强制任务拆解 planner（简单查询纯加延迟）
- 胖工具（自包方法论+重复调库）——归因=skill+原子工具
- circuit breaker / 静默重试（提前替没出现的问题写代码）

## 十三、已知问题 / 技术债

| 项 | 现状 | 备注 |
|----|------|------|
| Prompt/工具缓存单进程 | 多 worker 不跨进程生效 | 待 Redis pub/sub |
| 三库并存（生产 PG / db_ai_online / db_ai_test） | skill/规则/limits 改动需三库同步 | 已多次踩"改错库"；长期应收敛或做同步工具 |
| SSL 全局关验证（main.py） | 内网自签 CA 绕过 | 仅限内网部署 |
| 生成期过程清单不可点击 | 飞书流式卡平台限制 | 跑完即折叠 |
| 部分环境审计静默失败 | 收尾超时兜底吞错 | 账号表权限差异，统计页缺数据 |
